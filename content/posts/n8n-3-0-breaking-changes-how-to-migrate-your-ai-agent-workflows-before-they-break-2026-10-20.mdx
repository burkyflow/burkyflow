# n8n 3.0 Breaking Changes: How to Migrate Your AI Agent Workflows Before They Break

## Introduction

Your n8n AI Agent workflows will stop working on upgrade. n8n 3.0 removes the legacy AI Agent node and eliminates four execution modes without warning. If you manage automation pipelines, this isn't optional reading. It's a scheduling problem you need to solve this week. 

The n8n 3.0 breaking changes aren't cosmetic; they directly affect how your agents authenticate, execute, and return results. Teams that treat this as a routine version bump are the ones who'll be debugging production incidents at 2 a.m.

---

## What Actually Breaks in n8n 3.0

n8n 3.0 removes the legacy AI Agent node entirely. There's no backward compatibility layer, no fallback, and no grace period. If a workflow still references the old node, it won't gracefully degrade; it will fail.

Four execution modes tied to the legacy agent architecture are also deprecated:

- **ReAct Agent** → replaced by the unified **Tools Agent**, now the default execution mode for all AI Agent nodes
- **Plan and Execute Agent** → also consolidated into the **Tools Agent**, which n8n has supported as the recommended mode since version 1.82
- **SQL Agent** → deprecated in favor of combining the Tools Agent with dedicated database tool nodes
- **Conversational Agent** (legacy mode) → replaced by Tools Agent configurations using memory sub-nodes

Any workflow still referencing these modes won't just underperform. It will either fail silently (producing empty or malformed outputs) or throw hard execution errors the moment it runs on n8n 3.0.

## How to Audit Your Current Workflows

Before touching the upgrade button, run a structured audit across your environment:

1. **Use n8n's workflow export/search function** to flag every instance of the legacy AI Agent node across your workspace. Export workflows as JSON and search for node type references. This catches instances that aren't obvious from the visual canvas.
2. **Cross-reference execution mode settings** against the deprecated list (ReAct, Plan and Execute, SQL, legacy Conversational). Many teams set these modes once during initial build and never revisit them, which means outdated configurations hide in plain sight.
3. **Tag workflows by business criticality:** separate customer-facing automations (notifications, support ticket routing, billing triggers) from internal reporting or low-stakes tasks. This tagging becomes your migration priority list.

## Migrating to Agent v3: What Changes Operationally

Moving to the current Agent architecture (what n8n documentation refers to as the Tools Agent, the de facto "Agent v3" standard) isn't a simple node swap. Several operational details change:

- **Node configuration requirements**: Inputs for tools, chat, and memory are now distinct connection points rather than bundled settings. Workflows built on older agent types often need these inputs rewired manually. Several users on the n8n community forum have reported that upgraded nodes lose expected tool/chat/memory inputs if the underlying workflow wasn't rebuilt from scratch.
- **Execution mode mapping**: ReAct and Plan and Execute agents map to Tools Agent, but the reasoning loop behaves differently, so expect to re-test prompt behavior, not just node compatibility.
- **Memory handling**: Older workflows using implicit memory settings need explicit memory sub-nodes (Simple Memory, Redis, or similar) attached directly to the agent.
- **Credential and API call behavior**: Model binding is now more explicit. Credentials tied to specific model providers may need re-authentication after migration, especially if your workflow spans multiple LLM providers.

## Testing Before You Deploy

Migration without testing is just a different way of breaking production.

- **Set up a staging/sandbox environment** that mirrors production as closely as possible: same credentials structure, same trigger types, same data volume if feasible.
- **Run parallel execution**: keep the old workflow live while running the migrated version in staging against the same inputs. Compare outputs directly before any cutover.
- **Define rollback criteria in advance**: Decide what "failure" looks like (error rate threshold, output mismatch percentage, response time degradation) before you deploy, not while you're watching a dashboard spike in real time.

## Building a Migration Timeline That Doesn't Disrupt Operations

A workable sequence looks like this:


graph LR
    A[1. Audit Workflows] --> B[2. Staging Test]
    B --> C[3. Phased Rollout]
    C --> D[4. Monitoring Window]


1. **Audit & Tag**: Complete full workflow sweep and categorize by risk tier.
2. **Staging Verification**: Test highest-risk migration in staging environment with parallel runs.
3. **Phased Rollout**: Cut over in small batches starting with Tier 1 critical workflows.
4. **Monitoring Window**: Observe logs and error rates before starting the next batch.

Each stage has a clear exit criterion before moving to the next. Don't start phased rollout until staging tests have run clean for a defined period.

Set a hard deadline tied to n8n's version support lifecycle, not internal convenience. If legacy node support ends on a fixed date, your migration deadline should sit comfortably before that, not the week of, when there's no room to absorb unexpected issues.

Assign ownership per workflow, not per team. "The automation team owns migration" sounds reasonable but creates diffusion of responsibility: nobody is accountable for any single workflow's cutover. Naming one owner per workflow, even if it's the same person across several, keeps accountability specific and traceable.

## Summary

- **Audit all workflows** for legacy AI Agent node usage and deprecated execution modes (ReAct, Plan and Execute, SQL, legacy Conversational) before upgrading to n8n 3.0.
- **Migrate and test in staging** by risk tier, highest-impact, customer-facing workflows first.
- **Assign clear per-workflow ownership** and define rollback criteria before any production cutover.

The n8n 3.0 breaking changes aren't a surprise if you're reading this before the upgrade. Treat the audit as this week's priority, not next quarter's cleanup item. The cost difference between proactive migration and reactive incident response isn't marginal, it's measured in hours of downtime and customer trust.
